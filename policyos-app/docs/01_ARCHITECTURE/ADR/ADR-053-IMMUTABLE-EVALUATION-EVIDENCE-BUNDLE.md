# ADR-053: Immutable Evaluation Evidence Bundle

## Status

Accepted for Sprint 13 CP2-3.

## Context

ADR-050 defines immutable evaluation references, ADR-051 defines deterministic
plans, and ADR-052 defines execution lifecycle governance. PolicyOS now needs a
metadata-only way to associate evidence references with the exact plan and
execution record without collecting, loading, or interpreting evidence.

CP2-3 defines contracts, not evidence collection. Evidence presence does not
prove validity, and evidence validity does not prove evaluation correctness.

## Decision

PolicyOS introduces strict frozen contracts for evidence references, provenance,
lineage, opaque integrity metadata, explicit bundle versions, optional audit
metadata, bundle construction requests, and immutable evidence bundles. Pure
functions validate and construct bundles from caller-supplied contracts.

## Evidence reference model

An evidence reference contains caller-supplied identity, type, role, schema
version, opaque evidence and source references, optional media-type and integrity
references, timestamp, and ordinal. Evidence content is not stored. Prompt text,
model output text, payloads, and file bytes are not fields.

## Evidence type and role

Closed enums classify reference categories and their intended bundle use. Types
and roles express metadata intent only; they do not establish truth, quality,
completeness, admissibility, execution, or results.

## Evidence provenance

Provenance exactly binds plan, version, execution, run request, definition,
target, dataset, manifest, split, evaluator, registry snapshot and schema,
policy, plan authorization decision, execution authorization revision, actor,
agent, tenant, organization, offline tier, and planning fingerprint.

## Evidence lineage

Lineage exactly binds the plan, execution record, run request, delegation
lineage, plan version, and planning fingerprint. An optional transition reference
must identify a transition in the supplied execution history. No lineage is
generated, traversed, or resolved.

## Evidence integrity references

Integrity metadata is an opaque pointer with an explicit schema version and
optional opaque algorithm and signer references. Integrity references are not
hashes generated by PolicyOS. No digest calculation, signature verification,
certificate loading, cryptographic validation, or trust-chain evaluation occurs.

## Evidence bundle versioning

Bundle, contract, and evidence-schema versions are explicit and caller supplied.
They are retained exactly and never inferred or incremented.

## Exact plan binding

The bundle and provenance match every relevant immutable plan identity and
reproducibility reference. CP2-3 does not re-plan, resolve references, calculate
fingerprints, or alter plan tasks.

## Exact execution-record binding

The bundle, provenance, and lineage match the exact execution identity, context,
run request, actor, agent, authorization revision, and lifecycle history.
Evidence bundle construction does not mutate execution state or history.

## Lifecycle-state eligibility

Bundles are permitted for IN_PROGRESS, COMPLETED, FAILED, and CANCELLED records.
PLANNED, VALIDATED, and READY are rejected. Eligibility is governance metadata:
it does not prove external work occurred. COMPLETED is not proof of valid
evidence, correctness, or quality.

## Canonical ordering

Evidence ordinals are supplied by the caller, start at one, and are contiguous in
tuple order. Invalid order is rejected and never silently sorted.

## Duplicate rejection

Evidence identities, ordinals, and opaque evidence references must be unique.
Duplicates and conflicts fail closed; nothing is deduplicated or repaired.

## Authorization and access boundaries

Evidence provenance references the authorization already bound to the plan and
execution context. It creates no decision and stores no broad authorization
payload. Evidence references are not retrieval authority. Possession of a
reference does not authorize fetching its content.

## Reproducibility

Bundles retain exact plan version, dataset provenance, evaluator, registry
snapshot and schema, policy and authorization revisions, planning fingerprint,
lineage, and execution identity. Reference presence alone is not a
reproducibility claim, and no bundle fingerprint is calculated.

## Metadata-only audit exposure

Optional audit metadata contains caller-supplied IDs, counts, revisions, and
creation time. Counts and bindings must exactly match the bundle. Audit metadata
does not log or emit audit events.

## Fail-closed behavior

Unknown fields, invalid types, unsupported schema versions, ineligible lifecycle
states, noncanonical ordering, duplicates, timestamp conflicts, unknown
transitions, and binding mismatches are rejected explicitly.

## Security and privacy considerations

Contracts contain opaque references rather than raw evidence, prompts, outputs,
credentials, tokens, cookies, headers, provider responses, or stack traces. No
provider, model, MCP, connector, tool, filesystem, or network call occurs.

## Consequences

Callers must provide complete canonically ordered metadata and retain the exact
plan and execution record. Bundles are deterministic and inspectable, but they
make no claim about content existence, authenticity, validity, completeness, or
evaluation quality.

## Deferred scope

CP2-4 owns evidence validation. Later checkpoints own evidence collection,
metrics, scoring, ranking, judging, thresholds, aggregation, and gates.
Retrieval, dataset loading, persistence, APIs, queues, workers, schedulers,
events, telemetry, and tracing are also deferred.

## Alternatives considered

- Embedding raw evidence content was rejected to preserve the reference-only
  privacy and architecture boundary.
- Fetching references during construction was rejected because references are
  not retrieval authority and construction must perform no I/O.
- Automatically collecting execution evidence was rejected because CP2-3 is not
  an executor or collector.
- Generating hashes or fingerprints was rejected because integrity ownership is
  external and caller supplied.
- Mutable evidence lists were rejected because bundle history must be immutable.
- Silently sorting or deduplicating references was rejected because malformed
  caller intent must fail closed.
- Database-backed bundles were rejected because persistence is out of scope.
- Combining collection and validation was rejected because CP2-4 owns content
  validation.
- Treating COMPLETED as proof of valid evidence was rejected because lifecycle
  state is not evidence or correctness.
- Storing broad authorization payloads was rejected in favor of narrow exact
  identity and revision bindings.
