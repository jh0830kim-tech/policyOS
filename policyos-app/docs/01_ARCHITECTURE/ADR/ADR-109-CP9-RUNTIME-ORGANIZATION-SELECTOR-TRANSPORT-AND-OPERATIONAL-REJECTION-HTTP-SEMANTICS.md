# ADR-109: CP9 Runtime Organization Selector Transport and Operational Rejection HTTP Semantics

## Status

Accepted for the CP9 Runtime organization-selector and operational-rejection governance gate.
This decision changes no production or public Python, route, model, repository, schema, migration,
or PostgreSQL state.

## Context

ADR-100 fixes three Runtime endpoint paths and requires one validated organization selector, but
does not fix how that selector crosses HTTP. ADR-101 also leaves the bounded deadline-expiry and
disconnect envelopes to the later route contract. Choosing either detail inside production route
code would create unreviewed public transport meaning.

## Decision

### Exact organization selector transport

All three Runtime endpoints require exactly one query parameter named `organization_id`. The fixed
endpoint paths from ADR-100 remain unchanged. The parameter value is untrusted transport text and
must be the lowercase canonical hyphenated representation returned by `str(UUID(value))`. Missing,
empty, duplicated, non-ASCII, non-canonical, malformed, nil, or extra organization-selector aliases
fail with bounded `422` before request-capability scope creation, preparation inspection, rate
admission, facade invocation, or database work.

The route constructs `RuntimeApiOrganizationSelector` only from that validated UUID. It cannot
derive an organization from token claims, invocation, action, command, reconciliation,
idempotency, prepared facts, persistence, a default, or a latest/current row. The selector is not
authority. The facade still exact-revalidates tenant, organization, membership, classification,
permission, lineage, and persisted bindings. Missing or mismatched authoritative scope remains a
non-disclosing `404`; the transport `422` does not disclose whether an organization exists.

Query-parameter ownership preserves the already-fixed paths and avoids forwarding organization
identity as ambient proxy metadata. `X-Organization-ID`, body fields, cookies, token-derived
selection, path expansion, and accepting multiple locations with precedence are prohibited.

### Closed operational rejection mapping

Rate denial remains the only operational rejection mapped to `429`. It returns the existing
bounded public error envelope and the exact bounded `Retry-After` seconds from the durable rate
decision. A missing or malformed retry value fails closed and is not regenerated by HTTP code.

Deadline expiry and an observed disconnect both map to `503` with
`RuntimeApiErrorCode.DEPENDENCY_UNAVAILABLE`, the fixed message `Runtime operation unavailable`,
`retryable=true`, and no correlation reference unless an already-approved bounded correlation
reference is available unchanged. Capability absence, capability failure, missing preparation,
and missing production composition use that same non-disclosing `503` envelope. Public HTTP does
not distinguish their internal cause.

This shared envelope is intentionally not Runtime cancellation, timeout-state progression,
retry authority, compensation, success, effect termination, or proof that an external operation
stopped. Application code retains bounded typed internal reasons solely for ordering and tests;
responses and logs cannot expose package, callback, policy, deadline, observation, provider,
database, session, transaction, body, bearer, or cross-scope facts.

If the transport is already disconnected and no response can be delivered, the adapter makes no
second response attempt. It completes request-scope cleanup and may record only an existing
bounded correlation reference plus the generic operational-unavailable category through the
approved logging boundary. It never records raw request or preparation facts.

### Validation and ordering

Strict route/path/query/header/body validation and verified-claims authentication precede request
scope creation. Organization parsing precedes preparation inspection. Operational rejection
occurs only after one exact candidate inspection and consumes the package zero times. Successful
rate, deadline, and disconnect evaluation permits exactly one consumption and one facade call.
Error translation never retries, re-inspects, consumes, invokes the facade, or mutates Runtime
state.

### Persistence and migration

These are public transport decisions only. They add no durable owner, table, column, index,
trigger, backfill, normalization, deduplication, or migration `20260808_0025`. Migration
`20260808_0024` remains the single Alembic head.

## Validation requirements

- exact query parameter presence, canonical UUID syntax, duplicate and alias rejection;
- the same selector value passed unchanged to preparation and facade boundaries;
- transport-invalid `422` before request-scope creation and authoritative mismatch `404` after
  facade revalidation without existence disclosure;
- exact `429` rate mapping with persisted retry-after provenance;
- identical generic `503` envelopes for expiry, disconnect, capability/preparation absence, and
  capability failure;
- zero consumption and zero facade work for every rejected path;
- cleanup after an undeliverable disconnect without a second response attempt;
- no route import or call to ORM models, persistence repositories, adapters, or Workers; and
- Alembic single head `20260808_0024` with no migration `20260808_0025`.

## Alternatives rejected

- Organization header: proxy and ambient-header handling would add unnecessary identity context.
- Organization body field: query and mutation transport shapes would diverge and query has no body.
- Organization path segment: changes the fixed ADR-100 endpoint identities.
- Infer organization from claims or opaque references: authentication and request text are not
  organization authority.
- Map expiry or disconnect to `409` or `422`: neither is an exact-fact conflict nor malformed HTTP
  input.
- Add `408` or `499`: those codes are outside the approved CP9 error surface and would require a
  public-contract expansion.

## Consequences

Production routes can now implement one deterministic organization transport and one bounded
operational-rejection policy without inventing authority or status. The existing production
implementation scope may resume after this governance gate merges. CP9 remains Planned / Blocked
until production composition, PostgreSQL/HTTP acceptance, regression, and closeout merge. CP10
remains Planned.
