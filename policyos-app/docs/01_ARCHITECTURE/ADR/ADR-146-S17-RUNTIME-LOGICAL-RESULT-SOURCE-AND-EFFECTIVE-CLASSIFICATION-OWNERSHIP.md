# ADR-146: S17 Runtime Logical-Result Source and Effective Classification Ownership

## Status

Accepted for Sprint 17 vertical-validation governance.

## Context

Runtime authority and state validation permit a state, plan, audit trail, and effect to raise the
classification of an immutable execution request. A request persisted as `CONFIDENTIAL` may
therefore produce `RESTRICTED` execution-state, audit, logical-result, and effect facts without
lowering or replacing the request.

ADR-098 and ADR-099 instead required the execution request, state, audit, and logical result to
share one classification. Migration `20260808_0023` encoded that assumption by reusing the
logical-result classification in all three generic-revision foreign keys. PostgreSQL correctly
rejects a legitimate raised-classification result because the exact execution-request revision
still owns its original classification. Copying that request under a higher classification,
dropping relational proof, or changing an immutable revision would invent authority.

## Decision

### Two exact classification facts

The execution request owns one immutable **source classification** at its exact record ID and
revision. The execution state, audit trail, logical result, and deliverable effect own one
**effective classification** for the exact attempt. The effective classification must be equal to
or higher than the source classification under the closed PolicyOS classification order. A lower,
unknown, missing, substituted, cross-tenant, cross-organization, cross-request, cross-attempt, or
cross-lineage value fails closed.

Classification elevation is not reclassification of the execution request. No layer may rewrite,
clone, alias, or append the request solely to make its classification equal the effective
classification. The source classification comes only from the exact persisted execution-request
revision. The effective classification comes only from the already validated state/audit/result
scope. Neither value may be selected from a latest row, inferred from the other, or generated by
Persistence.

### Logical-result contract amendment

The later public-contract correction must carry `execution_request_classification` beside the
exact execution-request record ID and expected revision. The existing logical-result `scope`
continues to carry the effective classification. State, audit, logical result, and effect must
share that effective classification exactly; their existing equality checks are not weakened.

The query present locator and exact read result must preserve both classifications. The absent
locator still carries no logical-result identity, but its exact state and audit facts remain bound
to their effective classification. Query projection never combines, lowers, or hides the two
facts. Missing or mismatched source/effective classification fails before a projection is
returned.

### Relational ownership and migration

Migration `20260808_0025` is required as a separate schema gate. It must add a non-null
`execution_request_classification` to logical-result revisions and make
`fk_runtime_logical_result_execution_request` use that column. The state and audit foreign keys
continue to use the logical-result effective `classification`. A closed database constraint or
equally strong trigger must reject effective classification below source classification.

The identity table must continue to allow only one logical-result ID per tenant, organization,
execution request, and attempt. Classification cannot be used to create a second logical-result
identity for the same request and attempt. Exact revision and append-only constraints remain in
force.

The migration may populate `execution_request_classification` only by joining each existing
logical-result revision to its already referenced exact execution-request record type, tenant,
organization, record ID, and expected revision. It must first prove exactly one source row,
consistent source classification across revisions of the same logical result, effective
classification not below source, and no duplicate request/attempt identity. Missing, ambiguous,
duplicate, cross-scope, lowered, or inconsistent rows fail closed before any constraint is dropped
or data is changed. No latest-row selection, payload inspection, normalization, deduplication,
deletion, generated fact, or best-effort repair is permitted.

Populated downgrade fails before destructive DDL and leaves schema and data unchanged. Only an
empty logical-result store may remove the new constraint and column in dependency-safe order.

### Transaction and lifecycle boundaries

The facade remains the sole owner of the outer `AsyncSession` and root transaction. The active
Persistence helper may flush caller-supplied base/effect revisions before appending the logical
result so its exact foreign keys are visible, but it cannot begin, nest, commit, roll back, close,
or replace the session. Failure rolls back base records, effect initialization, logical result,
and transport receipt with zero residue.

Exact replay performs zero callback, classification derivation, local mutation, or logical-result
append. Execution projection and effect-delivery lifecycle remain separate authoritative results.

## Required gate sequence

1. Merge this governance correction.
2. Add the source/effective classification public contracts and validation.
3. Implement migration `20260808_0025`, model, serialization, and repository corrections in a
   separate persistence gate with fresh, populated, collision, downgrade, and rollback evidence.
4. Resume the preserved vertical-slice candidate only after both gates merge.

## Verification requirements

Later gates must prove equal and raised classification success; lowered, missing, substituted,
cross-scope, cross-attempt, and cross-lineage rejection; exact source-revision FK ownership; state
and audit effective-classification equality; one request/attempt logical-result identity;
append-only behavior; concurrent replay; rollback residue zero; populated migration fail-closed
behavior; and Alembic `20260808_0025` as the single head.

## Alternatives rejected

- Rewriting or cloning the execution request at the effective classification invents a new
  authoritative revision.
- Forcing all Runtime states to retain the request classification discards approved classification
  elevation and can lower derived sensitive facts.
- Storing the logical result at the source classification would make it lower than its state,
  audit, payload, or effect.
- Removing the execution-request foreign key or relying only on application equality loses the
  ADR-099 relational proof.
- Inferring source classification from the effective classification, payload, or latest request
  row is prohibited.

## Consequences

PolicyOS preserves immutable request identity and monotonic classification while retaining exact
relational ownership. This governance gate changes no production Python, public contract, model,
repository, schema, migration, database row, provider, credential, route, tag, or release. The
vertical validation remains blocked until the public-contract and `20260808_0025` persistence
gates are separately approved, implemented, merged, and validated.
